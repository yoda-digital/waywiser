Executive Summary

The Waywiser v2 blueprint is an architecturally rigorous design for a native Android personal intelligence runtime. Its security model, observation pipeline, and delivery tiering are production-grade thinking. Six parallel deep-research tracks validated every major technical assumption against current (August 2026) ecosystem state. Key finding Pi has a cross-backend conformance test suite

agent/src/harness/session/testing/conformance.ts (1,221 LOC) is designed to validate any session storage implementation against canonical semantics. It takes a SessionBackendFixtureFactory and runs identical tests against any backend. This is exactly the foundation blueprint §8 needs for differential Rust conformance testing.

Watch The reducer is the hardest porting target

The reducer.ts (744 LOC) contains the recovery FSM with corruption detection, TOCTOU guards, and complex queue semantics (steer/followUp/nextRun/deferred). This 750 LOC of TypeScript will become ~1,500 LOC of Rust due to explicit error handling and contains the densest invariants in the entire system.

High risk Romanian language quality unvalidated

Qwen3 shows "significant quality drops" on lower-resource languages and "garbled or repeated output" at the tail. Romanian is not in Qwen3's tier-1 language set. English and Russian are solid, but Romanian quality for processing calendar entries, notifications, and messages is unconfirmed. This must be validated empirically before committing the product to this model.

Medium risk Default overthinking wastes the single inference slot

The model defaults to "wildly overthinking" (community consensus). For an agentic loop with tool calls, this means wasted tokens and latency — directly harmful when the inference slot is shared. Mitigation exists (reasoning_effort: medium/low, thinking budgets) but must be integrated into the Pi agent loop from day one, not retrofitted.

Positive Strongest open 27B model for this workload

Qwen3.8-27B is the best available open model at this parameter count for agentic work. The single-model invariant (I6) is architecturally sound if read as "one authoritative model instance at a time" with a tested upgrade path — not "this model identity forever." The model alias architecture (§40) correctly abstracts this.

3. Kotlin↔Rust FFI — Bridge Architecture

UniFFI v0.32.0 (June 2026, Mozilla) is the production-grade choice. Used by Signal (libsignal), Firefox Android, Mozilla VPN. Generates Kotlin bindings from Rust interface definitions.

§78 RequirementSolutionEffort
Streaming eventstokio mpsc channel → UniFFI suspend fun nextEvent() or async callback trait~2 weeks
CancellationCancellationToken in Rust, signaled from Kotlin via separate FFI callLow
Activity destructionViewModel survives config changes; cancel from onCleared()Medium
Process recreationAll durable state in SQLite. Rust re-initializes from DB on restartHigh
Panic containmentcatch_unwind at every FFI boundary + panic = "unwind"Critical discipline
Large payloadsv0.32 zero-copy ByteBufferLow
BackpressureBounded tokio mpsc channelsLow
JNI ref leakageUniFFI manages most; uniffiIsDestroyed (v0.32) for custom callbacksOngoing
Gap UniFFI has no native streaming primitive

There is no Rust Stream → Kotlin Flow bridge built into UniFFI. The agent event stream must be built manually: either a polling suspend fun over a bounded channel, or a push pattern via async callback trait. Recommend a hybrid approach: UniFFI for the bulk API surface (memory, Brain, skills, permissions); hand-rolled JNI for the streaming event bridge where you need fine-grained backpressure and cancellation control.

Critical discipline One missed catch_unwind = instant production crash

UniFFI does not catch Rust panics. A panic in a JNI callback aborts the entire Android process. Every FFI entry point must be wrapped in std::panic::catch_unwind with panics converted to errors. Set panic = "unwind" in Cargo.toml (never abort). This must be enforced by CI lint, not developer memory.

Estimated FFI bridge effort: 6–8 weeks

For a senior engineer familiar with both Kotlin and Rust. The 90-day vertical spike should dedicate ~40% to this bridge. Start single-process (topology A); measure before splitting.

Precedent project

Operit (github.com/AAswordman/Operit) — an open-source Rust runtime + Android AI agent with llama.cpp/MNN support. Closest existing architecture to Waywiser v2.

5. Inference Serving Infrastructure

Blueprint correction Single-slot is a configuration, not a constraint

Blueprint §43 frames single-slot as a foundational limitation. In fact, OLLAMA_NUM_PARALLEL (default: 1) is configurable. At 2–4 slots, expect 20–40% per-request latency increase but 3–4x throughput. For Qwen 27B Q4_K_M (~19GB at 8K ctx), 2 parallel slots on a 48GB GPU (A6000) is feasible.

Serving engine comparison

EngineBest ForConcurrencyContinuous Batching
OllamaDev / single-user1–4 static slotsNo
llama.cpp serverSmall team (≤15)8–16 slots with -cbYes
vLLMProduction multi-userUnlimited (PagedAttention)Yes
SGLangMulti-turn agents/RAGBest for shared contextYes (RadixAttention)

Recommendation: Ollama for Foundation prototyping. For Product, migrate to llama.cpp server or SGLang — the API is OpenAI-compatible, so migration is a base-URL change. SGLang's RadixAttention is particularly valuable for Waywiser's multi-turn agentic workload with shared context prefixes.

Hardware reality

Qwen3.8-27B at Q4_K_M: ~16.4GB weights, ~19GB total at 8K context. Single RTX 4090 (24GB) is viable. 40–65 tok/s generation depending on GPU. For 2+ parallel slots, budget a 48GB card (A6000) or dual-GPU setup.

6. Accessibility, AppFunctions & Voice

Blueprint error AppFunctions is not available to Waywiser

The EXECUTE_APP_FUNCTIONS permission is restricted to system-level callers: Gemini, OEM assistants, and apps explicitly allowlisted by Google. A sideloaded third-party app cannot call AppFunctions. Blueprint §63's integration hierarchy must drop AppFunctions entirely.

Blueprint error ECM blocks AccessibilityService for sideloaded apps on Android 15+

Android 15's Enhanced Confirmation Mode (ECM) uses a system-level allowlist in /system/etc/sysconfig. Only factory-image packages bypass it. A sideloaded internal APK is blocked from enabling Accessibility and NotificationListener services by default. Mitigation requires either: (a) customizing the device factory image, (b) MDM programmatic grant, or (c) per-device ADB enablement.

Watch ROLE_ASSISTANT cleared on every APK reinstall

Known active bug (reported March 2026, affects even official apps). The assistant and voice_interaction_service Secure Settings are wiped on each update. For an internal app receiving frequent updates, this makes ROLE_ASSISTANT unreliable without a post-update MDM hook or ADB script.

9. Required Blueprint Corrections

Must fix (factual errors)

C-1
§63 — Remove AppFunctions from integration hierarchy. EXECUTE_APP_FUNCTIONS is system-only. Waywiser cannot call them.
C-2
§43 — Reframe single-slot as deployment default, not architectural constraint. OLLAMA_NUM_PARALLEL is configurable; the real constraint is GPU VRAM for concurrent KV caches.
C-3
§22 — Add ECM bypass requirement to Accessibility automation. Android 15+ blocks sideloaded apps from enabling AccessibilityService without factory-image allowlisting, MDM grant, or ADB.

Should fix (design improvements)

C-4
§52 — Add Gemma 4 E2B as primary edge candidate. It outperforms all three listed candidates and uses the better-supported LiteRT-LM runtime on Android. Recommend also adding FunctionGemma 270M as lightweight router.
C-5
§58 — Downgrade ROLE_ASSISTANT from "should support" to "optional enhancement." The reinstall bug makes it unreliable for a frequently-updated internal app. All baseline invocation paths are already independent of it.
C-6
I6 — Clarify invariant as "one authoritative model at a time" with a validated upgrade path, not a permanent model identity lock. The model alias architecture (§40) already supports this — the invariant wording should match.
C-7
New section — Add device provisioning requirements. The blueprint assumes internal distribution solves permissions, but ECM, battery optimization, and ROLE_ASSISTANT all require explicit device setup. A provisioning checklist (MDM configuration, ADB scripts, battery exemption) belongs in the blueprint.

10. Recommended Immediate Actions

A-1
Romanian language validation (Week 1). Run 200 diverse Romanian examples through Qwen3.8-27B: calendar entries, notification text, SMS/chat messages, mixed Romanian-English. Measure coherence, structured-output quality, and tool-calling accuracy. This is a go/no-go gate for the single-model bet.
A-2
Thinking-budget integration spike (Week 2). Test Qwen3.8-27B's reasoning_effort parameter (low/medium/xhigh) against representative Pi agent loop turns. Measure token waste and latency at each level. Establish per-priority defaults: P0 interactive = medium, P3 Brain reflection = xhigh, tool calls = low.
A-3
Port Pi conformance suite to language-agnostic fixtures (Month 1). Extract conformance.ts test cases into JSON/CBOR fixture files that both TypeScript and Rust implementations can consume. This is the single highest-leverage preparation for the Rust port.
A-4
FFI streaming spike (Month 1–2). Build a minimal Kotlin/Compose ↔ Rust bridge that streams agent events via bounded tokio channels. Test cancellation, Activity destruction, and process recreation. Study Operit's architecture. Allocate ~40% of the 90-day proof to this.
A-5
Device provisioning path (Month 1). Establish how company devices will bypass ECM for AccessibilityService and NotificationListener. Test MDM grant vs. factory-image allowlist vs. ADB script. This gates the entire device agency layer.
A-6
Edge model benchmark on actual S21+ (Month 2). Run Gemma 4 E2B via LiteRT-LM on the target device. Measure cold load, generation speed, memory, thermal behavior, and battery impact. Compare against FunctionGemma 270M for classification-only tasks. The blueprint's llama.cpp/Vulkan path is unlikely to work on Mali-G78.
